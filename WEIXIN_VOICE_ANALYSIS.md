# Weixin Voice Analysis

## Goal

Understand why Hermes / iLink Weixin voice replies do not arrive as native WeChat voice bubbles, and reduce the problem to a reproducible engineering conclusion.

## Scope

This analysis covered:

1. the helper project in this repository
2. Hermes Weixin source in `~/.hermes/hermes-agent`
3. the outbound media chain from local audio to iLink `sendmessage`

It did not attempt to reverse private WeChat protocols or modify the official WeChat client binary.

## What We Traced

### 1. Hermes helper project

We added and verified:

1. a standalone `.silk` generator from text or local audio
2. a native `.silk` experiment sender
3. a reliable audio file attachment sender
4. diagnostics for local Hermes / iLink account state

### 2. Hermes Weixin source

We confirmed that Hermes source still contains native outbound voice bubble logic in `gateway/platforms/weixin.py`.

Important observations:

1. `send_voice()` had been hardcoded to call `_send_file(... force_file_attachment=True)`
2. `_outbound_media_builder()` still had an active `.silk -> MEDIA_VOICE / ITEM_VOICE` branch
3. this meant the native voice bubble code still existed but was unreachable from the normal `send_voice()` path

### 3. Real media behavior

We verified:

1. `.silk` generation produced valid Tencent-style `SILK_V3` files
2. native `ITEM_VOICE` payloads were constructed correctly
3. audio file attachments reached the target chat
4. native voice sends could report success without appearing in the personal WeChat client

## Key Findings

### Finding A: local encoding is not the primary blocker

The `.silk` files generated by this project are real, non-empty, and structurally correct.

Observed indicators:

1. valid `SILK_V3` magic bytes
2. expected duration
3. stable file size and md5

### Finding B: Hermes source still supports native voice payload construction

The relevant Hermes code path still exists:

1. `.silk`
2. `MEDIA_VOICE`
3. `ITEM_VOICE`
4. `voice_item`

This means the problem is not "Hermes never implemented native voice bubbles."

### Finding C: the old fallback was explicit, not accidental

Hermes had been forced into file attachment behavior by an intentional `force_file_attachment=True` call in `send_voice()`.

That change disabled the native branch even though the branch itself still existed.

### Finding D: native voice can still disappear after a successful API call

This is the most important result.

We ran a controlled test where:

1. a marker text message was sent first
2. a native voice attempt was sent immediately after
3. the marker arrived
4. the native voice did not appear at all

That tells us:

1. the conversation context was valid
2. the target chat was valid
3. the send path was active
4. the failure happened specifically on the native voice message

## Engineering Conclusion

The current evidence points to an upstream limitation or filter in the public iLink bot path for personal WeChat accounts.

The reduced conclusion is:

1. local audio -> `.silk` works
2. `.silk` -> `ITEM_VOICE` payload works
3. Hermes can send the request
4. the personal WeChat client may still not render the message
5. `ITEM_FILE` audio attachments remain the only verified reliable delivery shape

## Current Usable Functionality

After cloning this repository, the baseline functionality that is verified to work is:

1. generate a real Tencent-style `.silk` file
2. inspect native voice payload construction
3. send a reliable Weixin audio file attachment
4. debug local Hermes / iLink configuration

This is the supported base capability of the project today.

## Why Native Voice Bubble Fails Today

Most likely reasons, in order of confidence:

1. public iLink bot outbound `ITEM_VOICE` is accepted by API infrastructure but not rendered by personal WeChat clients
2. public reference implementations expose voice payload schema without guaranteeing personal-client delivery support
3. additional private or internal fields may be required for true outbound voice bubble support
4. the supported path for real voice bubbles may only be the official WeChat client recording and sending the message itself

## What We Changed During Investigation

In this helper repository:

1. added `.silk` generation from text and local audio
2. added native `.silk` experiment commands
3. added reliable audio attachment fallback commands
4. added tests around voice payload generation and send behavior

In local Hermes source:

1. traced the real `send_voice()` and `_send_file()` path
2. re-enabled native voice behavior behind an experiment gate
3. verified that Hermes can reach the `.silk` native send path

## What We Did Not Prove

We did **not** prove that public iLink bot infrastructure can successfully deliver personal WeChat native voice bubbles.

That remains unproven and currently contradicted by observed behavior.

## Recommended Next Steps

### Practical product direction

Treat audio file attachment delivery as the current stable feature.

### Protocol-debug direction

If native voice bubbles remain important, add gated Hermes debug logs for:

1. `getuploadurl` key request fields
2. `sendmessage` key request fields
3. returned `ret / errcode / errmsg`
4. whether the send was `ITEM_VOICE` or `ITEM_FILE`

This would provide a proper upstream evidence bundle.

### Alternate implementation direction

If the product requirement is strictly "must appear as a WeChat voice bubble," the most credible fallback path is WeChat client automation:

1. open the real WeChat client
2. enter the target chat
3. feed audio into a microphone or virtual microphone path
4. let the client record and send the message itself

That path carries platform risk and account-risk tradeoffs, but it is the only remaining route that aligns directly with how personal WeChat normally creates voice bubbles.
